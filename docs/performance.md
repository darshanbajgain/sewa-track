# Performance: 100k requests, before and after indexes

> **Demo / portfolio project. All data is fake** (generated by `pnpm seed:large`).

Every number below was **measured**, not estimated, on the machine described at the end.
Method: measure the real queries → add indexes that match them → measure again → check the cost.

## Summary

| Query | Before | After | Speed-up |
|---|---|---|---|
| Officer queue (busiest ward, page 1) | 7.87 ms | **0.54 ms** | ~15× |
| Officer queue, overdue only | 11.28 ms | **0.42 ms** | ~27× |
| Palika admin queue | 14.74 ms | **2.79 ms** | ~5× |
| Request history (detail page) | 9.55 ms | **0.05 ms** | ~190× |
| Map: last 30 days, one service | 22.44 ms | **11.30 ms** | 2× |
| Map drill-down: palikas of one district | 28.90 ms | **23.54 ms** | 1.2× |
| Map: all districts, all time | 63.77 ms | **56.76 ms** | none (expected, see below) |

**End-to-end API latency** (100 sequential requests each, local, after indexes):

| Endpoint | p50 | p95 | Target (PRD §10) |
|---|---|---|---|
| `GET /stats/map` (national, overdue) | 58.0 ms | **66.3 ms** | p95 < 200 ms ✅ |
| `GET /stats/map` (drill-down, on-time rate) | 22.4 ms | **24.3 ms** | p95 < 200 ms ✅ |
| `GET /requests` (officer queue) | 3.6 ms | **5.2 ms** | p95 < 150 ms ✅ |
| `GET /requests?overdue=true` | 3.5 ms | **4.5 ms** | p95 < 150 ms ✅ |

**Cost of the indexes:** the 100k bulk insert went from **17.4 s to 38.4 s** (about 2.2× slower writes),
and `service_requests` now has 29 MB of indexes for a 24 MB table. Acceptable for a system that is read
far more often than it is written; for one-off bulk loads you would drop the indexes, load, then recreate them.

## 1. Data

`pnpm seed:large` (`apps/api/src/db/seed-large.ts`) generates **100,000** fake requests and ~165,000
audit events over the last 12 months:
- **Skewed by district**, like real demand: Kathmandu 13.8k, Morang 6.7k, Jhapa 5.5k, Rupandehi 5.2k, Sunsari 4.2k, …
- **65% closed** (mostly ISSUED), **35% open**, mostly recent; closing takes 0.2–2.5× the promised days, so some are late.
- One `CREATED` event per request + a final status event per closed request.
- After loading: `ANALYZE`, so the query planner knows the new table sizes.

## 2. How we measured

`pnpm db:explain` (`apps/api/src/db/explain.cli.ts`) runs `EXPLAIN (ANALYZE, BUFFERS)` on the API's
heaviest queries **using the exact SQL the repositories run** (imported from the repository files, not
copied), 7 times each, and reports the **median** execution time and the main plan nodes.
API latency: `curl -w %{time_total}` against the running API, 100 requests per endpoint, p50 and p95.

```bash
pnpm seed:large          # 100k fake requests (development DB only; replaces existing requests)
pnpm db:explain          # query timings + plans
```

## 3. Before: what the plans showed

| Query | Plan (main nodes) |
|---|---|
| Officer queue | `Seq Scan on service_requests` → `Sort` → `Limit` |
| Palika queue | `Seq Scan on service_requests` → `Sort` → `Limit` |
| Request history | `Seq Scan on request_events` (165k rows) → `Sort` |
| Map (all) | `Seq Scan on service_requests` → aggregate → `Sort` |

A **sequential scan** reads every row of the table. For "the 20 oldest requests of one ward" that means
reading 100,000 rows to keep about 100, then sorting them.

## 4. The indexes (migration `003_performance_indexes.sql`)

Each index matches a real query's `WHERE` + `ORDER BY`. **Column order matters:** equality filter first,
then the sort column, then the tie-breaker. Postgres can then read the matching rows **already sorted**
and stop after 20.

| Index | Serves |
|---|---|
| `service_requests (ward_id, submitted_at, id)` | officer queue: `WHERE ward_id = $1 ORDER BY submitted_at, id` |
| `service_requests (local_level_id, submitted_at, id)` | palika admin queue |
| `service_requests (district_id, submitted_at)` | map drill-down / district filters |
| `service_requests (service_type_code, submitted_at)` | map filtered by service + date range |
| `service_requests (citizen_id, submitted_at DESC)` | "my requests" (also indexes this foreign key) |
| `request_events (request_id, created_at, id)` | request history: Postgres does **not** index foreign keys automatically |
| `identity_checks (request_id, created_at DESC)` | latest identity check of a request |

**Deviation from the PRD's first guess.** The PRD planned `(ward_id, status, submitted_at)`. The queue sorts
by `submitted_at` and its status filter is optional, so with `status` in the middle the index can't deliver
rows in `submitted_at` order when no status is given. Measurement favoured `(ward_id, submitted_at, id)`.

## 5. After: what changed and why

| Query | New plan | Why it's faster |
|---|---|---|
| Officer queue | `Index Scan using service_requests_ward_queue_idx` → `Limit` | reads only that ward's rows, already in order: no sort |
| Overdue only | `Bitmap Index Scan` on the ward index → small `Sort` | only the ward's ~100 rows are checked for "overdue" |
| Palika queue | `Index Scan using service_requests_palika_queue_idx` | same idea, one palika |
| Request history | `Index Scan using request_events_request_idx` | 2–3 rows found directly instead of scanning 165k |
| Map, 30 days + one service | `Bitmap Index Scan using service_requests_service_date_idx` | reads ~7% of the rows |
| Map drill-down | `Bitmap Index Scan using service_requests_district_idx` | Kathmandu is ~14% of all rows, so the gain is small |
| **Map, all time** | **still `Seq Scan`** | it needs **every** row to count per district |

### The honest result: the national map didn't get faster
An index helps you **find a few rows**. The national map counts **all 100,000** requests, so reading the
whole table in one sequential pass is already the cheapest plan, and Postgres correctly ignores the
indexes. It still meets the target (p95 66 ms). If it ever didn't (millions of rows), the options are:
1. A **materialized view** of counts per district, refreshed every few minutes.
2. A **summary table** updated in the same transaction as each status change.
3. **Caching** the public response (it already sends `Cache-Control: public, max-age=60`).

## 6. Notes and limits
- One laptop, local Docker, no network between API and DB, warm cache: production numbers will differ.
  The point is the **relative** change and meeting the targets with margin.
- `count(*) OVER ()` in the queue counts all of the ward's matching rows before `LIMIT`; fine for a ward
  (about 100 rows), but a very large palika page would benefit from a separate, cached count.
- `OFFSET` pagination slows down on deep pages; keyset pagination (`WHERE (submitted_at, id) > (…)`) is the
  next step if queues grow to thousands per ward.
- Indexes were created with plain `CREATE INDEX` (inside the migration transaction). On a large live table:
  `CREATE INDEX CONCURRENTLY` to avoid blocking writes.

## Re-check after tuning the generator (2026-10-27)
The generator was later tuned so open requests are mostly recent (overdue share of open requests went
from ~97% to ~52%, which is more realistic). Re-measured with `pnpm db:explain` on the new dataset:
officer queue 0.47 ms, overdue-only 0.48 ms, request history 0.07 ms, national map 67.6 ms, drill-down
25.1 ms (all in line with the table above), and the palika queue **9.5 ms** (was 2.8 ms): the busiest
palika differs between generated datasets, and `count(*) OVER ()` counts all of its matching rows.
Still far below the 150 ms target.

Intel Core i5-1035G1 (8 threads), 15 GB RAM, PostgreSQL 16.15 in Docker (`shared_buffers` 128 MB,
`work_mem` 4 MB, defaults), Node.js 22.23.4. Measured 2026-10-26.
